# 0.3.0 — hosting the runtime in-process: what it actually requires

> **Reading this cold?** 0.2.0 runs a `logosctl` daemon beside the Electron app
> and talks to its `core_service` gateway over TCP. 0.3.0 was supposed to delete
> that daemon by hosting `core_service` inside the addon.
>
> **It turns out 0.3.0 does not need `core_service` at all.** The gateway exists
> so an *out-of-process* client has something to talk to. An in-process caller
> can invoke modules directly, over the default LocalSocket/QtRO transport, with
> no gateway, no TCP, and no token — which is the one thing a Qt-free JS client
> could never do. This was measured, not reasoned: see
> §[Experiment 2](#experiment-2-the-in-process-call-path).
>
> The C++ inventory is therefore roughly **one order of magnitude smaller** than
> the task assumed: about **120 lines**, not the ~1500 of `CoreServiceImpl` +
> dispatch + envelope.
>
> Every claim below has a repro target. Nothing here is projected from reading
> source alone.
>
> ```
> make exp-node EXP_MODE=none|pump|thread   the event-loop question, plain Node
> make exp-electron EXP_MODE=none|pump      the same, inside Electron + Chromium
> make exp-call                             an in-process caller vs. a real module
> make exp-call-electron                    the same, inside Electron
> ```
>
> The experimental code is in `scripts/exp-provider/` and is a **second addon**.
> It does not touch `src/addon.cc` or `binding.gyp`; `make verify` still passes.

## 1. The event-loop question: answered

`src/addon.cc` creates a `QCoreApplication` and **never runs its event loop**.
liblogos' load calls are synchronous, so 0.1.0 never needed one. The worry was
that publishing a provider and serving RPC would need a live loop, and that
running one inside Electron's main process would collide with Chromium.

**Verdict: pumping Qt's event loop from a libuv timer works, inside Electron,
with Chromium fully responsive. There is no collision.** The Qt/Chromium
coexistence risk that 0.1.0 avoided does not materialise.

### The experiment

`scripts/exp-provider/exp_addon.cc` is a ~200-line addon that does exactly what
`daemon.cpp:571` does — `new LogosAPI("exp_service", transports)`, a trivial
`LogosProviderObject`, `provider->registerObject(...)` — on a TCP transport, and
drives the Qt loop in one of three ways:

| `EXP_MODE` | how Qt's loop is driven |
| --- | --- |
| `none` | not at all — the 0.1.0 status quo |
| `pump` | `QCoreApplication::processEvents(AllEvents, 5)` from a JS `setInterval` |
| `thread` | a dedicated `std::thread` running `QEventLoop::exec()` |

A **separate process** then calls it with `logos-js-sdk` over plain TCP. Two
processes, because a client and a server sharing one event loop cannot
distinguish "the server never answered" from "the client never got to ask".

### Results

| host | `EXP_MODE` | port bound | `getMethods()` | `echo()` dispatch |
| --- | --- | --- | --- | --- |
| plain Node | `none` | yes | 0 | **hangs** |
| plain Node | `pump` | yes | 4 | **answers** |
| plain Node | `thread` | yes | 0 | **hangs** |
| Electron + live `BrowserWindow` | `none` | yes | 4 | **answers** |
| Electron + live `BrowserWindow` | `pump` | yes | 4 | **answers** |
| Electron, `QT_NO_GLIB=1` | `none` | yes | 0 | **hangs** |
| Electron, `QT_NO_GLIB=1` | `pump` | yes | 4 | **answers** |

The passing run, in full:

```
[exp] registerObject -> true, registryUrl=local:logos_exp_service_5834c7ca76e5, mode=pump
[electron] port 7411: LISTENING
[client] getMethods() -> 4: echo, getStatus, name, version
[exp] callMethodStd(echo) on thread 0x7ffff44f4500
[client] echo('hello') -> {"echo":"hello","served_on_thread":"0x7ffff44f4500","status":"ok"}
[electron] renderer executeJavaScript(1+1) -> 2

PASS(pump): provider answered RPC inside Electron AND Chromium stayed responsive
```

Chromium's health is checked *after* the RPC, and not merely for "did not
crash": the renderer is made to execute JavaScript and return a value. An RPC
that worked by wedging the UI would not be a result worth having.

### Three things the table says that are worth stating plainly

**A dedicated Qt thread does NOT work.** `thread` fails everywhere. The
`QTcpServer` and its socket notifiers are created on the thread that called
`registerObject()` — the JS thread — and Qt objects are serviced only by an
event loop running on the thread they are affined to. A `QEventLoop::exec()` on
a *different* thread never touches them. Moving the runtime to its own Qt thread
is the obvious-looking design and it is wrong unless the Qt objects are
*constructed* there too. This is worth recording because it is exactly the shape
`README.md` currently recommends ("a real app would move the runtime to its own
thread that owns the Qt event loop").

**Inside Electron, `none` passes — and that is a coincidence, not a guarantee.**
Electron links glib (`libglib-2.0`, `libgio-2.0`), and Qt on Linux defaults to
`QEventDispatcherGlib`, which attaches its sources to the same process-default
`GMainContext` that Chromium's main-process message loop drives. So Chromium
pumps Qt's events for free.

This was not inferred — it was tested. Setting `QT_NO_GLIB=1` forces Qt onto its
own UNIX dispatcher, and the Electron `none` result flips from PASS to FAIL
while everything else stays identical:

```
$ ... EXP_MODE=none QT_NO_GLIB=1 npx electron scripts/exp-provider/exp-electron.js
[electron] port 7415: LISTENING
[client] getMethods() -> 0:
[client] echo failed: echo did not answer within 12000ms
FAIL(none): client=2 chromium=true
```

**So: pump explicitly anyway.** `pump` passes in all four configurations —
Node and Electron, glib and no-glib. Depending on the glib coincidence would
make the app's correctness hostage to an Electron upgrade, a `QT_QPA_PLATFORM`
change, or a non-Linux port. The cost of not depending on it is one
`setInterval`.

  npx electron scripts/exp-provider/exp-electron.js   # expect FAIL
```

### A token is mandatory, and its absence looks exactly like a hang

The first `pump` run still failed, with a signature this repo has now seen three
times: **introspection worked (4 methods over TCP), dispatch hung.** The cause
was not the transport. The provider process had not registered an inbound
credential, so `ModuleProxy` had nothing to match the caller's token against —
and the failure mode is *silence*, not a refusal.

Adding the two calls the daemon makes fixed it outright:

- server side: `TokenManager::instance().saveInboundToken(caller, token)`
  (`daemon.cpp` step 8 — **`saveInbound`, not `saveToken`**; the store is
  direction-split, and the outbound spelling files it under "what I send *to*
  that caller", where the inbound check never looks)
- client side: `logos.saveToken('exp_service', token)`

`NEXT.md` already records this trap for the 0.2.0 route ("A stale token does not
produce an auth error — the call simply never answers"). It is the same trap,
and it is worth stating as a general rule for this codebase: **on the Logos RPC
surface, a missing or wrong token is indistinguishable from a dead transport.**

## 2. Experiment 2: the in-process call path

This is the experiment that changes the plan, and it was worth running before
writing any `CoreServiceImpl`.

`CoreServiceImpl::callModuleMethod` (`core_service_impl.cpp:494`) — the whole
reason the gateway exists — reduces to two lines once the error shaping is
stripped away:

```cpp
LogosAPIClient* c = m_api->getClient(QString::fromStdString(module));
c->invokeRemoteMethod(module, method, args, Timeout(), &err);
```

Nothing about that is privileged to a daemon. So `scripts/exp-provider/exp_call.cc`
does it directly from the addon: `logos_core_init/start`, a plain
`LogosAPI("core_service")` with **no transport set at all**, and one
`invokeRemoteMethod`.

```
$ make exp-call

[exp-call] origin=core_service module=delivery_module method=getAvailableConfigs
[logos] Module loaded: delivery_module
[exp-call] loadModule(delivery_module) -> true
[delivery_module] DeliveryModuleImpl::getAvailableConfigs called
[delivery_module] Cannot get available configs - context not initialized. Call createNode first.
[exp-call] ok=true code= origin=
[exp-call] value={"error":"Context not initialized","success":false,"value":null}

PASS: an in-process caller invoked a real module method
```

`ok=true` is the round trip succeeding. `"Context not initialized"` is
**delivery_module's own answer** — it wants `createNode()` first. That is
byte-for-byte the result the 0.2.0 gateway route produced through a whole
`logosctl` daemon (`NEXT.md`, "Status of that confirmation"), obtained here with
no daemon, no gateway, no TCP port, and no token.

Arguments marshal correctly too — the module echoes the value it received:

```
$ ... EXP_METHOD=getNodeInfo EXP_ARGS='["default"]' node scripts/exp-provider/exp-call-host.js
[delivery_module] DeliveryModuleImpl::getNodeInfo called with nodeInfoId: default
ok=true
```

A JS string crossed `nlohmann::json` → `QVariantList` → QtRO → the module's real
C++ signature. And inside Electron with a live window:

```
$ make exp-call-electron
[exp-call] loadModule(delivery_module) -> true
[exp-call] ok=true
[exp-call] renderer executeJavaScript(1+1) -> 2
PASS: in-process module call inside Electron, Chromium responsive
```

### Why this works here and not from the JS SDK

`NEXT.md` establishes at length that a Qt-free consumer cannot invoke a module:
`capability_module` publishes **0 methods** over a plain transport, so the SDK's
per-target token lookup dials a surface with nothing behind it and waits forever.

An in-process caller never goes near that path. It speaks the **default
LocalSocket/QtRO transport** — the one every module already publishes on, the
one the modules use to talk to each other, and the one `capability_module`
*does* publish its handshake on. The `make verify` log shows it happening
between two modules already:

```
[capability_module] Saving inbound token for caller: "delivery_module"
[capability_module] ModuleProxy: Token saved for module: "delivery_module"
```

The addon is simply another Qt participant on that bus. **The entire
plain-transport limitation that blocked 0.2.0 is out of scope for 0.3.0** — it
was a constraint on Qt-free clients, and the addon is not one.

This also retires the question `NEXT.md` leaves open about needing a
`TokenManager` on the hot path: with `LogosAPI` constructed in-process, the
token manager is the process's own, and the handshake it participates in is the
same one modules use among themselves. No token plumbing was needed for
Experiment 2 at all.

## 2b. Experiment 3: event subscription — the item with no evidence

§5.2 below named this "the next experiment to write", on the grounds that it was
the only inventory item with zero experimental backing. It has now been written
(`scripts/exp-provider/exp_event.cc`, `make exp-event`) and it **passes**, with a
real Waku node:

```
[exp-event] onEventWhenAvailable(delivery_module::) -> id=1
[exp-event] ARMED=true (callback on thread 140737347878144)
[exp-event] pending after 3s: (none)
[exp-event] createNode -> ok=true in 9 ms: {"error":null,"success":true,"value":null}
[exp-event] start -> ok=true in 0 ms: {"error":null,"success":true,"value":null}
[exp-event] EVENT connectionStateChanged: ["Connected",1789654052305925000]
[exp-event] EVENT nodeStarted: [true,"",1789654052312625400]

PASS: 2 event(s) delivered to JS from an in-process subscription
```

The node is genuinely on the network — the module's own log shows
`relayCount=6`, a `WakuMetadata` exchange with `remoteClusterId=ok(2)` and eight
shards. This is the first time anything in this repo has started a Waku node.

**The subscription arms during the publish gap.** It was taken immediately after
`loadModule` returned, with no settling delay, which is precisely the window
`core_service_impl.cpp:598` warns about — a module is marked loaded before it
publishes its object, and `requestObject()+onEvent()` is silently refused there.
`onEventWhenAvailable` armed anyway and `pendingEventSubscriptions()` was empty
3s later. The lesson that file records is correct and was worth reusing.

**The callback arrives on the JS thread.** `140737347878144` is the same thread
that called `setup()` and that the pump runs on — unsurprising in hindsight,
since `processEvents()` from a libuv timer is what services the Qt objects, and
they are affined to the thread that created them. A `ThreadSafeFunction` is
still the right mechanism (nothing promises this stays true, and the C++
signature hands back `std::function` with no thread guarantee), but the
reentrancy risk in §5.5 is now the live concern rather than a cross-thread data
race: an event callback can re-enter JS while JS is on the stack.

### Two things that cost a run each, and are not written down anywhere else

**`onEventWhenAvailable` ARMS ON AN EVENT NAME THAT DOES NOT EXIST.** The first
run subscribed to `nodeStarted` and got `ARMED=true` and silence. Arming means
the *module* was reached; it says nothing about whether the event name is one
the module emits. So "armed but silent" is indistinguishable from a typo, and an
experiment that checked only `armed` would have scored a misspelling as a pass.
This is why `make exp-event` reports arming and delivery as separate outcomes
with separate exit codes (3 = never armed, 4 = armed but silent, 0 = delivered).

**The event callback is not wired until `createNode` succeeds.**
`delivery_module_plugin.cpp:207` calls `logosdelivery_set_event_callback` only
on the success path of `createNode`, so *no* event can reach *any* subscriber
before then, however early the subscription armed. An experiment that subscribed
and waited without calling `createNode` would have observed silence and drawn
exactly the wrong conclusion.

### What the module actually emits, which the README got wrong

`README.md` listed `nodeStarted(bool,QString,int)` and
`connectionStateChanged(QString,int)` as Qt signals. Two corrections, both from
reading `logos-delivery-module/src/delivery_module_plugin.h:23-51` and then from
the run above:

- There is **one** Qt signal, `eventResponse(QString, QVariantList)`. The names
  below are event *names* carried in its first argument, not separate signals,
  and every payload element is a `QString`.
- The plugin's documented set is five: `messageSent`, `messageError`,
  `messagePropagated`, `messageReceived`, `connectionStateChanged`. `nodeStarted`
  appears nowhere in `logos-delivery-module`'s source — and **is nonetheless
  delivered at runtime**, as the log above shows. It comes up through the
  liblogosdelivery FFI layer rather than the plugin's own mapping table. Worth
  stating plainly because both readings were defensible and only the run settled
  it: the source-derived list is incomplete.

Which is the argument for subscribing with an **empty event name** — the
wildcard `LogosObject::onEvent` has always understood as "every event on this
object" (`core_service_impl.cpp:598`, since logos-protocol#74). It is the right
subscription for a log pane, it cannot be misspelled, and it is the only form
that would have caught `nodeStarted`.

### The config `createNode` accepts

`createNode(QString)` takes a **JSON document**, not a config name. Passing
`"default"` answers `createNode cfg is not valid JSON`. `{}` parses and starts a
node with nobody to dial, which is silent — the "log goes quiet" problem in a
new costume. A `preset` populates entry nodes, cluster id and sharding together:

```json
{"mode": "Core", "preset": "logos.test"}
```

Valid presets are `""`, `twn`, `logos.dev`, `logos.test`, `status.prod`. `twn`
is the RLN-protected Waku Network and needs a registered membership this PoC
does not have. `src/gateway.js` reached the same config independently for the
0.2.0 route, which is a useful cross-check: the module semantics are the same
whichever transport drives them.

### Unavoidably C++

| # | what | why it cannot be JS | size |
| --- | --- | --- | --- |
| 1 | `LogosAPI` construction + ownership | `QObject` subclass with a C++ ctor; koffi cannot construct one, and `getClient()` hands back a C++ object with vtable dispatch | ~10 lines |
| 2 | `LogosAPIClient::invokeRemoteMethod` | C++ virtual method over QtRO; the value crosses as `QVariant`. **This is the irreducible core of 0.3.0** | ~25 lines |
| 3 | `nlohmann::json` ⇄ `QVariantList` marshalling | `logos::nlohmannArgsToQVariantList` / `qvariantToNlohmann` are C++ free functions in `liblogos_protocol.so`. Already written upstream — just called | ~5 lines |

| 5 | Async dispatch off the JS thread | `invokeRemoteMethod` blocks; a 20 s default `Timeout()` on Electron's main thread freezes the UI. `Napi::AsyncWorker`, or `invokeRemoteMethodAsync` + `ThreadSafeFunction` | ~40 lines |

**Total: roughly 120 lines**, appended to `src/addon.cc`, in the shape it already
uses.

### Explicitly NOT needed

This is where the plan shrinks, and each line is a direct consequence of
Experiment 2:

| thing | status | why |
| --- | --- | --- |
| `CoreServiceImpl` (695 lines) | **not needed** | it is an RPC *gateway*. In-process callers do not need a gateway to reach themselves |
| `core_service_dispatch.cpp` (228 lines) | **not needed** | a string-to-method `if/else` chain that exists to route *wire* method names. JS calls `call(module, method, args)` directly |
| `call_envelope.{h,cpp}` (205 lines) | **not needed** | it disambiguates "method returned null" from "call failed" *over the wire*. In-process, `logos::CallError` already carries `code`/`message`/`origin` separately from the value |
| `package_ops.{h,cpp}` (690 lines) | **not needed** | package install/plan/apply. This PoC installs modules with `lgpm` at build time |
| `LogosProviderObject` subclass | **not needed** | nothing out-of-process needs to call the app |
| `LogosAPIProvider::registerObject` | **not needed** | ditto — publishing is what a *server* does |
| `TokenManager` / `saveInboundToken` | **not needed** | no inbound RPC to authenticate. Experiment 2 needed no token at all |
| `setTokenValidator`, `TokenStore` | **not needed** | operator-issued tokens are a multi-client daemon concern |
| TCP transports, port allocation | **not needed** | the default LocalSocket transport is what modules already publish on |
| `logosctl` in the AppImage | **deleted** | ~100 MB and a second copy of the runtime |

Everything in `src/addon.cc` today (init, start, `loadModule`, `knownModules`,
log capture, …) stays exactly as it is.

### Staying in JS

Argument/result shaping, the `getStatus` / `listModules` conveniences (already
covered by the bound C ABI: `modulesInfoJson`, `loadedModules`), retry and
timeout policy, the event fan-out to the renderer over IPC, and all UI. The
addon's JS surface grows by two functions:

```js
await core.callModule(module, method, args)   // -> parsed result
core.watchModule(module, event, callback)     // -> unsubscribe fn
```

## 5. Open questions and risks

**Honest ones, not reassurance.**

1. ~~**`createNode()` has not been called.**~~ **RETIRED — it has, and it works.**
   §2b: `createNode({"mode":"Core","preset":"logos.test"})` answered
   `success:true` in 9 ms, `start()` likewise, and the module's log shows a node
   on the network with six relay peers. The node runs in the Electron main
   process with no daemon. What remains untested is *longevity* — every run here
   is under a minute, and nothing has exercised a node across a sleep, a network
   change, or an hour.

2. ~~**No event subscription has been tested.**~~ **RETIRED — see §2b.** It
   arms during the publish gap, and events reach JS through a
   `ThreadSafeFunction`. Two traps found in the process are recorded there:
   arming does not validate the event name, and the module wires its event
   callback only after `createNode` succeeds. The callback arrives on the JS
   thread, which makes §5.5's reentrancy question the live one.

3. **`invokeRemoteMethod` blocks, with a 20 s default timeout.** On Electron's
   main thread that is a frozen UI. Item 5 in the inventory is not optional
   polish. `loadModule` already has this problem and the repo accepts it at
   59 ms; a network call is a different proposition.

4. **The pump interval is unmeasured.** 5-10 ms was picked arbitrarily and
   nothing here characterises latency or CPU cost against it. A timer that fires
   200 times a second in an idle app is a battery question nobody has asked.

5. **Reentrancy is untested.** `processEvents()` from a libuv timer can dispatch
   a Qt event that re-enters JS while JS is already on the stack. Experiment 1's
   provider is trivial and single-threaded. A real workload with overlapping
   calls could surface this, and it would look like corruption rather than a
   clean failure.

6. **The glib coupling is undocumented upstream.** §1 pins the mechanism
   empirically, but nothing in Qt's or Electron's documented contract promises
   it. Explicit pumping makes the app independent of it; that independence
   should not be quietly given up later.

7. **macOS and Windows are entirely unknown.** All of this is Linux. The glib
   dispatcher does not exist on either other platform, and on macOS Chromium and
   Qt both want to own `NSApplication`'s run loop. That is the classic hard case
   and none of it is tested here.

8. **`QT_QPA_PLATFORM`.** Experiments run `offscreen` under Node and unset under
   Electron (matching `make run`). Not varied, not proven irrelevant.

9. **Version coupling.** This binds the addon to `liblogos_qt_host.so`'s C++ ABI,
   not just the C ABI. `logos_api.h` carries an explicit ABI warning about its
   private member layout being consumed by plugins that link the host runtime.
   The C ABI was a deliberate insulation layer, and 0.3.0 gives it up — a
   liblogos bump can now break the addon at load time rather than at compile
   time.

## 6. Recommendation

**Do 0.3.0. It is smaller than 0.2.0 and strictly better, and the two
experiments above are most of its risk already retired.**

What it buys, concretely: one process instead of two; no `logosctl` in the
AppImage (~100 MB and a second copy of the runtime); no per-boot token file, no
`~/.logosctl` session directory, no daemon config, no TCP ports, no daemon
lifecycle to supervise; and no plaintext tokens on a loopback socket. It also
sidesteps the two unresolved 0.2.0 problems in `NEXT.md` outright — the
silently-dying daemon on a `local`+`tcp` transport list, and the stale-token hang
— because neither exists without a daemon.

The honest caveat: **0.2.0 should still land.** It is nearly done, it is the
route that proves `createNode()` actually starts a node, and that proof is
reusable by 0.3.0 unchanged. 0.3.0 replaces *transport*, not module semantics.

### The smallest viable first step

Not "port `CoreServiceImpl`". This, in order:

1. **Write the event-subscription experiment** (`exp_event.cc`,
   `onEventWhenAvailable` → `ThreadSafeFunction` → JS). It is the only inventory
   item with no evidence, and the one most likely to surface something ugly.
   Half a day.

2. **Add `callModule` to `src/addon.cc`**, as a `Napi::AsyncWorker` so it does
   not block the main thread. Link `-llogos_qt_host -llogos_protocol` in
   `binding.gyp`. Start the pump in `start()`. About 80 lines, all of it already
   written and proven in `exp_call.cc`.

3. **Drive `createNode()` through it** — behind the existing button, no UI work.
   That is the moment 0.3.0 overtakes 0.2.0, and it is one method call away from
   where Experiment 2 already stops.

If step 1 reveals that event delivery needs something the pump cannot give,
that is worth knowing for the price of half a day — and 0.2.0 is still there.
